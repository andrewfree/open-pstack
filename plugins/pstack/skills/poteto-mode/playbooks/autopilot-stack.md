### Autopilot-stack

**You own the stack, never the landing. Hand the operator one linear stack of verified PRs to review and land.** **Autopilot-full** holds except for how verified work leaves. Each tick re-reads both playbooks from disk (`skills/poteto-mode/playbooks/autopilot-stack.md` and `autopilot-full.md` under the installed plugin), and this one wins where they differ.

1. **Run Autopilot-full's owners, minus the landing.** Resolve the forge, `<base-repo>`, `<head-remote>`, `<head-url>`, and `<base-remote>` as Autopilot-full step 2 does; this playbook never merges. When the head repository is a fork, validate its identity and record its owner and repository name as `<fork-owner>` and `<head-name>`. Owners report STACK-READY with the exact head SHA in place of merge-ready. They never rebase onto another branch, trunk included, and never retarget, merge, close a PR, or arm auto-merge, because the root owns the chain's topology and the operator owns the landing. When an item depends on another, its owner branches from that item's branch, not from trunk. Nothing enters the stack before a clean verdict from Autopilot-full step 4.
2. **Give the topology one writer.** Owners push only their own branches and report each tip, its current patch base, and its intended parent. Only you rebase or retarget a link, because two writers on one chain undo each other. Append each clean PR to one frozen bottom-to-top list in dependency order, or an order the operator specified. For same-repository heads, the forge's base-branch chain also records that order. For fork heads, every PR targets trunk, so never infer stack order from their equal base branches. Never require Graphite (`gt`). An owner takes your push as its new base and lease, and on a conflict resolves its own slice for you to push.

   Before you rebase, force-push, or retarget an existing PR, apply Shipping step 4's disarm-and-confirm rule to that PR and every descendant, stopping if the forge cannot confirm every request off. Fetch trunk through `<base-remote>`. Fetch another stack branch directly through `<head-url>`, because `<head-remote>` may have the base repository as its fetch URL and the fork as its push URL. Validate the chosen repository identity through the active forge, and record the fetched target as `<parent-tip>`. Before rebasing, record the child branch's published SHA as `<captured-sha>` with `git ls-remote -- "$head_url" "refs/heads/$branch"` and require it to equal the local pre-rebase tip. Require `git merge-base --is-ancestor "$current_base_sha" "refs/heads/$branch"` to pass. When the parent changed, move only the child's commits with `git rebase --onto "$parent_tip" "$current_base_sha" -- "$branch"`, then record `<parent-tip>` as the child's new patch base. Publish with `git push --force-with-lease="refs/heads/$branch:$captured_sha" -- "$head_url" "HEAD:refs/heads/$branch"`. When the head and base repositories are the same, create or retarget the child PR with the parent branch as its base. Use `origin pr create --status open --base "$parent_branch"`, `gh pr create --base "$parent_branch" --repo "$base_repo"`, `origin pr edit "$pr" --base "$parent_branch"`, or `gh pr edit "$pr" --base "$parent_branch" --repo "$base_repo"` according to the resolved forge and operation. When the head repository is a fork, keep the local child branch rebased onto its parent's exact tip but create or retarget every PR against `<trunk>` in the base repository. With GitHub, capture the approved PR title and body as `<title>` and `<body>`, then create it with `gh api --method POST "repos/$base_repo/pulls" -f "title=$title" -f "body=$body" -f "head=$fork_owner:$branch" -f "head_repo=$head_name" -f "base=$trunk" --jq .html_url`; add `-F draft=true` only when Opening a PR's readiness rule requires a draft. Otherwise use the resolved Origin equivalent. Retarget it with `gh pr edit "$pr" --base "$trunk" --repo "$base_repo"` or the resolved Origin equivalent. A forge cannot use a fork-only parent branch as a PR base.
3. **Absorb drift at the root.** Until landing starts, fetch current trunk through `<base-remote>` and rebase the chain bottom-up with step 2's explicit old-base and new-parent flow. When a rebase surfaces conflicts in an owner's files, that owner fixes its own slice and you push the result using step 2's captured-SHA lease flow. A rebase rewrites every SHA above it, so apply the patch-id rule in `playbooks/shipping.md` step 3 link by link, since a link's base is its parent, using each PR's recorded patch-base-to-head diff. Anything no longer valid goes back through Autopilot-full step 4 before delivery. Re-run mergeability and CI after every rewritten push even when the patch ID is unchanged.
4. **Deliver the chain, then keep your hands off it.** The deliverable is the frozen bottom-to-top list, reviewable in the resolved forge, and each link carries its verdict in its PR. Same-repository heads use a base-branch chain. Fork heads retain local parent ancestry while every PR targets trunk. The operator sends only the current bottom PR through Shipping, one at a time. A merge-when-ready request applies only to that bottom after Shipping has disarmed and confirmed every descendant; never offer or arm merge-when-ready for the chain as a whole or for a descendant. Once landing starts, nobody writes to the chain except the post-merge move that Shipping step 4 sanctions, because a second writer breaks a landing in flight. A mid-landing problem goes through you to the operator, and any fix waits for the operator's go.

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** catch the operator up per the **ketchup** skill, with links to the stack root and tip, a one-line verdict per link, and anything parked or excluded with the reason.
