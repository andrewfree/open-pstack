# Provider routing

Select `claude:provider-routing` and `codex:provider-routing` for changes to saved Claude pool selection, provider dispatch or its validator. Keep the existing `runner` feature when its separate explicit-pin or external-runner behavior changes. This feature has one case per harness. A verifier change adds the two `project-skill` self-tests, producing four top-level sessions and exactly one actual nested Claude child.

Both parents load the exact installed candidate `pstack:poteto-mode`. Each resolves twelve fresh nonce-bound synthetic scenarios using installed routing instructions. Expected decisions remain in trusted verifier memory, outside the fixture and prompt. The cases cover saved pool versus direct alternatives, direct and named overrides, unavailable pool and pin refusal, shortened catalog refinement, numeric model revisions, exact registered model pins, omitted default effort, unsupported effort, generic-driver refusal, a manual host choice, and the Claude parent's native Agent route. They launch no models and never masquerade as native MCP results. A passing checker unit test proves only the oracle; an installed parent must produce the decisions in a source/body-validated native session.

The Codex case uses T3's app transport, never plain `codex exec`. Its fixture sheet saves the prepared pool-backed verification instance, with no explicit operator override. That instance is already bound to the selected daily pool through the strict reference/host checks in `t3-app.md`. Live native capabilities must also show the daily pool, an eligible direct-login alternative and a manual host fallback. A targeted daily-primary lookup is required before dispatch. A shortened family listing requires bounded native refinement under installed policy.

The installed `resolve-t3-claude-route` helper must run after the native catalogs and before the only delegate. Its native JSON output must have `selectionSource: sheet`, `quota: unknown`, the exact concrete model and high effort, and the same target that is delegated unchanged. The retained request must contain the exact fixture sheet, null operator override and actual projected native provider data, including all four relevant profiles. Synthetic replacement catalogs, a forced direct pin, a helper result without native execution order, and a route change after validation fail the case.

The child task must complete with this run's unique `PONG <nonce>`. Match native catalog, delegate/task/thread/run identities, async plan interaction, terminal result, actual Claude Agent SDK launch and init, candidate plugin path, skill source/body, healthy T3-only MCP inventory and fixture output. A PONG file, catalog entry, quota value, helper output or dispatch handle by itself is insufficient. Raw child evidence remains independently mandatory in `t3-app.ts`.

Preparation requires permanent pool and Codex verification profiles. The default shared-reference policy requires matching explicit references. An owner-authorized independent-client policy instead compares public route metadata while T3 holds each client credential separately; it makes no credential-equality claim. Until the selected policy is prepared, report `pool-verification-unprepared`. No verifier task provisions keys or settings, resolves secrets, or substitutes direct login.
