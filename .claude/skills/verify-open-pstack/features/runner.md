# Runner and provider dispatch

## Sub-features

Strict argument validation, parent/provider routing, external child launch, prompt delivery, output and receipt persistence, and failure reporting; inspect the diff for which branches changed.

## How to get to it (user POV)

Invoke the installed parent workflow (`poteto-mode`, `arena`, or `swarm` as documented by the candidate) in the fresh native harness. Have that parent dispatch its documented external-provider lane.

## Driving it with verify-open-pstack

Read the candidate's `pstack-runner --help` and installed mapping through the native skill. Use a run-owned fixture and fresh output/receipt paths. Exercise all changed provider lanes without changing parent routing. Retain the native parent/child transcript, provider receipt, output, and concrete fixture effect. Confirm provider/model/effort/access mode match the requested route and output belongs to this invocation. Exercise changed invalid-input/failure branches as well. Keep direct runner tests in a separately labeled local-CLI artifact, never as the installed-harness result.

## Gotchas

Provider children retain real `HOME`, `USER`, and `LOGNAME` and the native-login arrangement in `isolation.md`: normal Claude config/login with session-only candidate plugin flags, and run-owned Codex config with auth symlinked to the daily login. Temporary and GitHub state remain run-owned; never pass publisher credentials. No credential reading/copying, source flags, or extra login is required. Missing file-based Codex auth fails closed. State separation is not an OS access-denial guarantee.

Do not add implicit timeouts or weaker-model fallbacks. A model assertion that a child ran is insufficient; inspect the actual receipt and output. Never reuse output from another SHA or run.

## Headless

The runner recipe in `recipes.ts` has the installed `poteto-mode` parent launch the candidate `pstack-runner` for one external lane: from Claude, the first lane of the installed catalog's `bug-fix` role default, and from Codex, the first lane of its `feature, refactoring` role default. The case fails before launch if the installed catalog's route table does not list that lane's provider, or routes it natively or through the T3 Claude Agent route from this parent. It asserts the launcher command ran from the installed plugin, the receipt reports `complete` with the requested parent, provider, model, effort, and mode, and this session wrote the output. `verify.sh run --runner-route PROVIDER:MODEL@EFFORT` replaces the route for each parent whose provider differs. The flag accepts any provider name; the installed catalog decides whether the route exists and is external, so a new provider such as Devin needs no verifier change. A Kimi route such as `kimi:kimi-code/k3@max` needs the `kimi` CLI and macOS `sandbox-exec`; the live gate already runs only on the operator Mac. Seatbelt profiles do not nest, so every route case starts Codex with `danger-full-access`; a Claude parent whose Bash tool runs in Claude Code's own sandbox gets a `child-failed` receipt that names the nested sandbox, and the case fails.

From Codex the recipe also adds `app-route-1`, which needs `--t3-app`: a T3 Codex parent with the run-owned installation dispatches one read-only lane on the T3 Claude Agent route to the Claude verification instance, for the first T3 lane of the candidate's `judgment and prose` role default or the `claude:` route given with `--runner-route`. The parent must look up its own catalog with `orchestrator_capabilities` before `delegate_task`, pick the newest concrete revision for a rolling alias (an exact pin unchanged), pass the requested effort in an async, plan-mode request with a client request id, drain the task to a completed `PONG`, and write the lane record and output that `provider-dispatch.md` names. The verifier checks the parent's choice against the coordinator's fresh catalog and binds the Claude child to its own native log; see `t3-app.md`. Then the recipe adds the `claude-route-refusal` case: the installed `poteto-mode` parent runs the candidate launcher once for a read-only Claude Opus lane, with a recording `claude` guard first on `PATH`. The shell command succeeds only when that runner exits exactly 78, so the existing successful-command parser can observe the expected refusal; runner exit 0 and all other failures make the shell check fail. It asserts the receipt is `route-refused` with that route and this session's paths, records no executable, command or preflight, leaves the output unreserved and both stream sidecars empty, and that the guard never ran. It runs in `codex exec`, which has no T3 tools, so it covers the runner side of the route only. Route overrides do not change this case. The former `linked-worktree-writer` case dispatched a Codex-parent Claude writer, which the runner now refuses, so the Claude writer's shared `.git` denial has no live consumer.

From Claude the recipe adds the `full-access-writer` case. Its fixture sheet puts `feature, refactoring` on `codex:gpt-6.1-sol@max` and holds the line `codex writer sandbox: full-access`. The prompt names the sheet, the role and the lane's paths, never the runner flag. The child writes a per-run nonce to `.agents/result.json` in its cwd, and adds a second nonce that it reads from the DOM headless Chrome dumps for a fixture page (Playwright's Chromium when Chrome is absent). The page file holds that nonce only base64-encoded. The case asserts the receipt is `complete` for that route and cwd, records `writerSandbox: "full-access"` and carries `--sandbox danger-full-access` in its argv, and that the `.agents/` result written this session holds both nonces. Its counterpart, `bounded-writer`, uses the same dispatch from a fixture sheet that puts `feature, refactoring` on `codex:gpt-6.1-sol@low` and has no setting line. The child writes a per-run nonce to the plain file `result.json` in its cwd, which `workspace-write` allows; it uses no browser and no `.agents/` path. The case asserts the receipt is `complete` for that route and cwd, records `writerSandbox: "bounded"`, carries `--sandbox workspace-write` and never `danger-full-access` in its argv, and that `result.json` written this session holds the nonce. Docker is not exercised. Route overrides do not change these cases.

`runner:t3-kimi-cliproxy` is a separate feature. Classification reaches it wherever it reaches `runner`, so a PR that changes only the selected T3 Kimi CLIProxy route names it without running the external-lane, Claude-route or writer cases. It has one case per harness and needs `--t3-app` with the operator's `kimiRoute` (see `t3-app.md`). Its T3 parent runs the run-owned installation: the Codex verification instance, or the Claude verification instance with the exact candidate plugin. The prompt gives the operator's selection: the provider instance, the exact proxy model, the service tier, and a `kimi:` descriptor with an explicit effort. It does not name the lane-record route, the target option keys or the dispatch mode; the installed `provider-dispatch.md` supplies them. The case fails before launch unless the installed catalog still routes that descriptor through the external runner from this parent, so the T3 dispatch can come only from the conditional rule.

The case asserts the installed `poteto-mode` load and rejects execution of `pstack-runner` or the Kimi CLI while allowing reference searches containing those names. It requires exactly one native `delegate_task`, after an `orchestrator_capabilities` result in which the selected instance is an eligible `codex` driver without constraints and lists the exact model, whose `reasoningEffort` and `serviceTier` options include the requested values. The coordinator's fresh catalog must agree. The target contains only the selected instance, exact model and options `{ reasoningEffort, serviceTier }`; environment, project, driver and runtime overrides are refused. The async, plan-mode request has a client request id, the test role and the exact bounded PONG-only task with this fixture's grounding directory. Every `task_status` must name that task and follow its dispatch result, none may report a pending question or approval, and one must report the dispatched child thread and run completed with the same instance, model and options, nothing pending, and a `PONG` summary. A subsequent `t3_thread_read` must retain the original child's complete activity. The private lane record must hold `route: "t3-kimi-cliproxy"` with the matching descriptor, target, effort, request and task identities, and the output must be `PONG`, both written this session.

Evidence includes the parent's native T3 tool records and the actual Kimi child's Codex-driver native lifecycle, prompt, model and final PONG, bound to the original fresh T3 child activity. Native call and result positions establish catalog, dispatch and completion order. For this case only, the Claude parser allows `orchestrator_capabilities`, `delegate_task`, `task_status` and `t3_thread_read` from the native `t3-code` server at top level, each listed in the session's tool inventory, and reads each result as JSON; any other result counts as empty. Every other Claude case still rejects all MCP tools. A later Claude prompt passes only as T3's completion notification for that dispatch. The Codex case keeps the Claude launcher pass-through and binds no Claude child. The Kimi child runs on the operator's selected instance, which the verifier does not arm or edit. The child needs independent native lifecycle evidence, while candidate-plugin and run-owned home checks apply to the parent under test. Retained child evidence receives hashes with the rest of the case artifacts. The recorded target and options are request evidence. They do not prove the served model, and the live run's Kimi quota use does not prove separate paid billing.
