# Model catalog

Changes to either `docs/model-routing/correctness-first-<parent>.md` profile are catalog changes, even when no plugin file changes. Explanatory documentation keeps its existing classification.

The trusted preparer records whether each profile exists in the pinned commit's Git tree. A catalog run omits only the profile case for a harness whose profile was never shipped in that candidate. It does not infer this from the mutable candidate filesystem. A declared profile that is missing or changed still fails source verification before exercise. The pre-install session count is a conservative maximum that includes optional profile cases; the same limit applies to that maximum.

## Sub-features

The generated model catalog (`plugins/pstack/skills/poteto-mode/references/model-catalog.md`), the generated Claude-native `pstack-<family>-<effort>` agents, and the runner registry sources they come from (`scripts/runner/registry/**`, `scripts/runner/providers/**`): model matrix, kept predecessors and rolling aliases, routes, provider notes, and role defaults.

## How to get to it (user POV)

A parent reads the catalog through `provider-dispatch.md` whenever a configured role launches. Invoke the installed `poteto-mode` skill and ask it to resolve roles from a model sheet.

## Driving it with verify-open-pstack

Give the parent a fixture model sheet, not the operator's configured one, so this feature changes no real configuration. Ask it to report each role's descriptors and routes as JSON. Compute the expected role defaults and routes from the installed candidate's catalog and the fixture sheet, never from a copy in the verifier.

## Gotchas

The outcome is the evidence: the reported descriptors and routes must equal the candidate's. Do not check which files the parent read or the text of its commands. A catalog change also selects `setup` and `runner`, because setup reads the catalog and the runner resolves lanes through the registry.

## Headless

The catalog recipe in `recipes.ts` writes a fixture sheet whose `judgment and prose` line takes another role's default descriptor, so only a read of the sheet reports it. The sheet has no `arena runners` or `bug-fix` line. It puts `swarm workers` on `codex:gpt-6-luna@max`, `hardest tasks` on the registered pin `claude:claude-opus-5-5@max`, `how explainer` on the versioned `claude:claude-sonnet-5-5@high`, `how explorer` on the Devin lane `devin:swe-2@max`, `interrogate reviewers` on the OpenCode lane `opencode:opencode/deepseek-v4.1-flash-free@max`, and the writer role `perf-issue` on the Kimi lane `kimi:kimi-code/k3@max`, whose provider lists both `read-only` and `isolated-write`. The parent writes `routes.json` with the descriptors and routes of those nine roles. The case asserts the `poteto-mode` load and that the report equals, role by role, the sheet's descriptor or the installed catalog's role default, each with the route the catalog's route table gives this parent. The pin, Luna, the Devin, OpenCode and Kimi lanes stay unchanged, those three lanes are external from both parents, and the Sonnet revision is reported as `claude:sonnet@high`. The recipe fixes those dispatched descriptors, and the catalog gives their routes. The sheet also puts `feature, refactoring` on `codex:gpt-6.1-sol@max` and holds the setting line `codex writer sandbox: full-access`. The report adds that role and `writerSandbox`, the `--writer-sandbox` value the parent would pass for that role's writer: `full-access` from Claude, whose route is the external runner, and null from Codex, whose route is native `spawn_agent`. A second case, `consume-sheet-bounded`, writes the same fixture sheet with the setting line `codex writer sandbox: bounded`. The runner's `bounded-writer` case covers a sheet with no setting line. It asserts the same roles, descriptors and routes, and `writerSandbox` null from both parents, so a parent that passes full access without the opt-in fails.

On Claude, `native-agents` has the parent dispatch `pstack:pstack-sonnet-max`, `pstack:pstack-opus-5-5-max`, and `pstack:pstack-haiku-5-5-max` through `Agent` with `run_in_background: false`. Each child reads its own fixture nonce, writes it to its own output file, and replies with it as its final answer. The case asserts each dispatch, at least one tool call recorded under it, that the output file holds that agent's nonce, and that the `Agent` call's own result holds that nonce. A launch notice in place of the report fails the case, so it proves the report came back inline. Codex has no Claude-native agents, and its session record does not show `spawn_agent`, so this case runs on Claude only.

Both harnesses also run `consume-correctness-profile`. It copies the exact bytes of `docs/model-routing/correctness-first-<parent>.md` from the provenance-checked candidate workspace into the fixture, then invokes the installed `poteto-mode` parent to report all 15 roles. Before launch, the recipe checks the complete role set against the installed catalog and every assignment against the profile contract: Sol high for general work, Astra high for hardest tasks and code panels, Opus high for judgment and critique, Luna high for the Codex reader or Haiku high for the Claude reader, and unchanged `inherit-parent` descriptors for Why and Reflect. Routes come from the installed candidate catalog, including native inherited roles, native Codex models from Codex, external Codex models from Claude, and the T3 Claude route from Codex. The report must explicitly read the bounded writer setting and report no full-access writer flag. The assertion requires the native skill load, the complete ordered report, and unchanged profile bytes; both the report and profile are retained as evidence. This case resolves routes without launching a lane or changing daily configuration. Select `claude:runner` with `--runner-route codex:gpt-6-astra@high` separately to exercise the registered Astra lane through the installed runner.
