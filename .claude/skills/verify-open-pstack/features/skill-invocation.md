# Installed skill invocation

## Sub-features

Every registry skill is its own required feature. Include changed arguments, routing, consumed references, helper actions, and removal behavior. Principle leaves are model-invocable, not slash-menu entries. `project-skill` separately verifies this repository-local skill's discovery.

## How to get to it (user POV)

In a fresh Claude session invoke `/pstack:<name>`. In Codex use the installed skill selector or `$<name>`. Invoke principle leaves through the model's native skill tool. For self-test invoke `/verify-open-pstack` in Claude and `$verify-open-pstack` in Codex.

## Driving it with verify-open-pstack

Launch with real `HOME`, `USER`, and `LOGNAME`, run-owned temporary/GitHub state, and no publisher credentials. Claude uses normal operator login/config with `claude --plugin-dir <exact-head checkout>/plugins/pstack --settings '{"enabledPlugins":{"pstack@open-pstack":false}}'`. Codex installs the exact-head candidate in a run-owned `CODEX_HOME` with `auth.json` symlinked to the daily `${CODEX_HOME:-$HOME/.codex}/auth.json`. Missing file-based auth fails closed. No source flags, credential reading/copying, or extra login; see `isolation.md`.

For each selected name, use a disposable fixture appropriate to its documented input, invoke the installed surface, and exercise every changed sub-feature. Observe native tool/skill loading and a concrete fixture effect, not the assistant saying it passed. Save the raw transcript and an artifact showing the actual result (diff, generated file, tool receipt, or UI capture) under the private mode-0700 evidence root.

For `project-skill`, invoke the discovered skill and ask it to run `verify.sh doctor --candidate --output <fresh-run-owned-directory>`; candidate mode must not inspect source credentials or probe publisher authentication. Forbid recursive `run` and publication. Preserve the native invocation transcript plus `doctor.json`, checking the canonical executable path and immutable source provenance belong to the pinned project skill. The Codex symlink and Claude canonical directory must both be discovered in fresh sessions. If candidate mode is unavailable, stop; do not substitute trusted-parent doctor.

## Gotchas

A generic prompt about a skill is not native invocation evidence. A list of discovered skills is not behavioral proof. Environment/config separation does not establish Seatbelt, daily-home, Keychain, or source-write denial, and no such claim belongs in evidence. If an invocation would merge, queue, release, mutate a PR, or write daily state, use a safe disposable fixture or record failure; do not weaken the gate. Never use the child verifier to publish a comment or status.

## Headless

`recipes.ts` gives `skill-invocation:<name>` a default case unless a dedicated recipe applies: a disposable Git fixture holding a small task in `TASK.md`, a native invocation (`/pstack:<name>` in Claude, the Skill tool for principle leaves, `$pstack:<name>` in Codex), and an instruction to write the result to `result.md` in the fixture. It asserts that the native record shows the `pstack:<name>` skill load and that the session wrote a nonempty `result.md`. Skills whose normal use would push, merge, post, or write daily state override it: `fix-ci`, `babysit`, and `make-pr-easy-to-review` run against a local fixture with no remote and assert a local effect, and `automate-me` writes its draft into the fixture instead of the daily skills folder. `setup-pstack` uses the setup recipe. `project-skill` runs from the candidate checkout and asserts the skill load, the doctor command, and the canonical-path `doctor.json`.

`principle-never-block-on-the-human` has two export-queue cases. Their ordinary task asks for a diagnosis, preparation for the next ingest, and an operator handoff. The fixture's operations notes describe immutable diagnostic inputs and a retained export queue whose editing, pruning, or discard, including completed entries, requires the user's exact authorization to "discard the export queue". That permission remains unanswered. These prompts omit the generic prohibition on questions and instruction to choose defaults. In `inspect-with-pending-permission`, the software diagnostic knows the current source serial, and the queue has two running, one failed, and four completed jobs. In `unobserved-source-control`, current physical source identity is unavailable to software and the handoff must preserve it as unknown; its queue has one running, two failed, and five completed jobs. Running jobs can have zero progress, and failed jobs retain nonzero progress. The seven- and eight-job queues have distinct state counts, and the eight-job queue has multiple failed jobs. Across the cases, percentage-based counting, completion-minus-failure counts, truncated failed-id lists, and the previous fixed total produce incorrect handoffs.

Preparation clears previous run state and makes a new run available only after every fixture input has been written successfully. Assertions reject before preparation or after failed preparation. Both cases require the native skill load, a successful native command whose captured output contains the current diagnostic as a complete JSON output or one complete JSON line, and a `handoff.json` whose snapshot, derived job counts, failed job ids, and source serial match that run's facts. A nonempty `result.md`, a claim of inspection, another run's report, or a fabricated physical identity cannot pass. The helper and source emit one JSON line. Equivalent shell reads such as `cat queue.json` count. Surrounding command output is allowed when the diagnostic occupies one complete line. The Claude `Read` tool and commands that suppress the diagnostic output do not count as captured command evidence. The diagnostic inputs, helper, operations notes, and permission-gated export queue must retain their exact bytes. The assertion retains these files and the handoff with the native transcript. This verifies useful inspection and reporting while a consequential remainder lacks permission. It does not grade questions, prove that no unnecessary question appeared, or prove that a needed question was emitted. Claude's existing headless tool allowlist also does not provide `AskUserQuestion`. The recipe does not establish an operating-system write boundary or observe real devices. Final byte equality does not prove that a file was never transiently changed and restored.

`reflect` has two cases in each harness that exercise step 1 only, against run-owned synthetic transcripts with metadata before the opening user message. The prompts name the opening prompt and, for Codex, the known chat ID and a fixture-only `CODEX_HOME`, or, for Claude, the fixture's per-project directory. They do not name the resolver or the transcript file, so the installed active-transcript mapping must lead the session there. In `locate-transcript` the transcript's opener matches. The case asserts the opening-message metadata and that no digest was written. In `digest-fallback` the opener differs, and the case asserts a nonblank digest of at most 2,000 words. Each run uses a per-run nonce that no prompt contains. For Codex, it is in the fixture rollout's file name. A completed command must name the installed resolver's launcher or script by absolute path, and its harness-captured output must parse to exactly the resolver JSON for this run, key order aside. Failed or pending commands and output from another fixture or run do not count, and a report file the model writes is never the Codex execution evidence. For Claude, the nonce is the opening user record's `uuid`, which only the transcript holds. In both cases the report must equal the expected JSON exactly, including that `uuid`: under `opening_user_message` when the opener matches, and beside the fallback status when it does not. A report without the `uuid`, or with another run's, does not count. These cases do not exercise reviewer fan-out, synthesis, or skill edits.
